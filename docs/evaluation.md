# Evaluation

Generated by `ml/evaluation/evaluate.py` and `ml/evaluation/find_failures.py`.
The live artifacts are `ml/evaluation/evaluation_report.json` and
`failure_report.json`, served at `GET /api/v1/evaluation` and rendered on the
Research page. The numbers below are from the current run.

> **REGIME WARNING.** Every number on this page was computed on the offline
> **bootstrap** corpus: the human class is 36 hand-authored seed essays, and the
> machine classes come from a template generator and a rule-based editor. These
> metrics measure **how separable those three generators are**. They are not an
> estimate of performance on real student essays and must not be quoted as one.

## Protocol

- **Model selection**: `GroupKFold` (≤4 folds) over `group_id`, on the **training
  split only**. Selection metric macro F1.
- **Calibration**: Platt scaling fit on the **validation split**.
- **Reporting**: the **test split**, used nowhere else in the pipeline.
- Splits are made over groups, stratified by label signature and the L2-English
  flag; held-out topics and one held-out generator are forced into test.

| ---------- | --------: | ----: | -----------: | ----------: |
| train      |       398 |       |              |             |
| validation |        89 |       |              |             |
| **test**   |   **128** |    31 |           65 |          32 |

Shipped model: `hybrid::lightgbm`, 411 features, Platt-calibrated.

### Confusion matrix

Rows are true labels, columns predictions:

|                  | → human | → ai_generated | → ai_polished |
| ---------------- | ------: | -------------: | ------------: |
| **human**        |      23 |              0 |         **8** |
| **ai_generated** |       0 |             65 |             0 |
| **ai_polished**  |       6 |              0 |            26 |

Two things this makes plain, and the accuracy figure hides:

**1. Human recall is 0.742.** Eight of 31 human essays were classified as
machine-polished. That is the failure mode with real consequences: if this were
pointed at real applicants, roughly a quarter of honest writers would be flagged.
No human essay was called fully machine-generated, which is some comfort, but not
much.

**2. `ai_generated` is perfect, and that is a red flag.** Precision and recall of
1.000 with AUC 1.000 does not mean the detector solved the problem — it means the
offline template generator is trivially separable. It draws sentences from a finite
bank, so surface and corpus-similarity features pull it apart completely. Expect a
substantially lower and more useful number once real model output replaces it. The
training run emits a `separability_warning` when this happens.

The real difficulty sits between `human` and `ai_polished`: 14 of the 14 total
errors are confusions between those two classes. That is expected by construction —
a lightly polished essay *is* mostly human text.

## Does the hybrid approach actually help?

Each feature set refitted on train with an **identical RandomForest** and scored on
test. Only the feature set varies, which is what makes this controlled.

| Feature set            | Features | Macro F1 | Accuracy | Human recall |
| ---------------------- | -------: | -------: | -------: | -----------: |
| **hybrid**             |      411 | **0.852** |    0.891 |        0.806 |
| hybrid_no_shift        |      382 |    0.841 |    0.883 |        0.774 |
| baseline_stylometric   |      246 |    0.830 |    0.875 |        0.839 |
| lm_only                |      118 |    0.767 |    0.828 |        0.710 |

| Comparison                | Δ macro F1 |
| ------------------------- | ---------: |
| hybrid − baseline         |     +0.022 |
| hybrid − lm_only          |     +0.085 |
| hybrid − no_shift         |     +0.011 |

> The `hybrid` row is **not** the shipped model. The shipped model uses whichever
> estimator won grouped CV (LightGBM), so its headline metrics differ slightly.
> Holding the estimator fixed here is deliberate — otherwise a feature-set
> comparison would be confounded by estimator choice.

**Answers:**

- **Do LM features add value on top of stylometry?** Yes, but modestly: +0.022
  macro F1. Training CV standard deviation is ~0.01–0.05, so this is a real but
  small effect, not a decisive one.
- **Are LM features sufficient alone?** No. `lm_only` is the weakest set by a clear
  margin (−0.085). Perplexity-style measurements are not enough on their own.
- **Does within-document style shift help?** +0.011 — a small positive effect,
  inside CV noise. It is retained regardless, because the per-paragraph style-shift
  analysis is a **user-facing output in its own right**: it is what lets the UI
  point at the specific passage that differs from the rest of the essay. Dropping
  the features to chase a difference this corpus cannot resolve would remove that
  evidence.
- Note that `baseline_stylometric` has the *best* human recall (0.839). Adding
  features improved macro F1 while making human false positives slightly worse —
  worth knowing, and not visible from a single headline metric.

sentences / 120 words.

## Generalisation

### By topic and by generator

Six topics and one generator persona appear in **no** training document.

| Slice                 |  n | Recall for `ai_generated` |
| --------------------- | -: | ------------------------: |
| Held-out topics       | 20 |                     1.000 |
| Topics seen in training| — |                     1.000 |
| Held-out generator    | 21 |                     1.000 |
| Generators seen in training | — |                 1.000 |

These slices contain **only** `ai_generated` documents, so macro F1 and accuracy
are not comparable with the multi-class slice — the report flags them
`single_class: true` and reports recall instead. (An earlier version of the
evaluation reported "macro F1 1.000 on held-out topics", which was an artifact of
scikit-learn inferring labels from a single-class slice. It is fixed, and the
metric is now label-consistent with the confusion matrix.)

**So: the machine class transfers cleanly across unseen topics and an unseen
generator. Whether *human* writing generalises is unknown**, because no human
documents are in these slices. That is a real gap in the evaluation design, not a
result, and closing it needs more human data.

### By length

| Band                | n  | Macro F1 |
| ------------------- | -: | -------: |
| long (≥ 256 words)  | 22 |    1.000 |

**Short documents are markedly worse**, and this is expected rather than a bug:
every distributional estimate behind these features — variance, entropy,
percentiles, z-scores — is noisy at low sentence counts. It is also the argument
for the 120-word abstention floor.

## Bias analysis

**Question:** does the detector disproportionately flag human writing from
second-language English writers?

**Metric:** false-positive rate on human documents — of the human essays in a
group, what share were called machine-written or machine-polished — with a Wilson
95% interval.

| Group                    | Human docs | FP rate | 95% interval    |
| ------------------------ | ---------: | ------: | --------------- |
| `l2_english_simulated`   |          5 |   0.200 | 0.036 – 0.625   |
| `l1_english`             |         26 |   0.269 | 0.137 – 0.461   |

Difference −0.069 (ratio 0.74), **intervals overlap heavily**.

**Conclusion: no statistically distinguishable disparity at this sample size. This
is NOT evidence of fairness — it is a sample-size limitation.** With 5 L2 documents
the interval spans 4% to 63%; that range is consistent with anything from "no
problem" to "flags two out of three".

**Severe limitation, restated because it matters:** the L2 subset consists of seed
essays written in a **simulated** second-language register, not writing collected
from real L2 authors. These numbers show that the pipeline *can* measure such a
disparity. They do not establish that the detector is fair to real second-language
writers. Published work consistently finds AI detectors over-flag L2 English
writing, and nothing here contradicts that.

> An earlier run could not produce this measurement at all: stratifying splits by
> label alone put every L2 seed into train/validation, leaving zero L2 human
> documents in test. Splits are now stratified by the L2 flag as well. Finding that
> required reading the bias output rather than assuming it worked.

## Feature importance

Permutation importance on the validation split — how much accuracy actually depends
on each measurement. Read from the trained model, not hardcoded.

| # | Feature                                   | Group       | Importance |
| -: | ---------------------------------------- | ----------- | ---------: |
| 1 | `cor_char_sim_delta_ai_human`             | corpus      |    0.1048 |
| 2 | `agg_mean_sty_sentence_initial_transition`| stylometric |    0.0221 |
| 3 | `agg_std_sty_sentence_initial_transition` | stylometric |    0.0209 |
| 4 | `agg_p75_sty_comma_rate`                  | stylometric |    0.0209 |
| 5 | `whole_lm_mean_prob`                      | lm          |    0.0172 |
| 6 | `agg_p25_sty_punct_density`               | stylometric |    0.0160 |
| 7 | `agg_std_syn_pos_propn`                   | syntactic   |    0.0148 |
| 8 | `doc_mean_syllables_per_word`              | structural  |    0.0148 |

Reference-corpus similarity dominates by a factor of five. That is the feature most
exposed to a narrow training corpus: with ~36 independent human documents the human
centroid is a poor summary of human writing in general. **It is the first thing
that should improve when real essays are added**, and the reason to be sceptical of
these results transferring.

The next tier is sentence-initial transition words ("Moreover,", "Furthermore,") —
a genuine machine-register signal, and also one the offline generator produces on
purpose, so its rank here is partly circular.

## Confidently wrong examples

`find_failures.py` finds the highest-confidence errors and explains each from the
model's own feature contributions. 14 errors in 128 documents; 11 above the 0.55
confidence threshold. The three most confident:

### 1. `h018-original` — human → ai_polished, confidence 0.72

A hand-authored seed essay about learning to cook, called machine-polished.

- Burstiness and corpus-similarity features dominated the decision.
- The measurements that triggered it describe **register, not authorship**: a human
  writing formally and evenly produces the same numbers as a machine.
- *Improvement:* burstiness is a genuinely weak signal for individual documents and
  should carry less weight; it also needs an interaction with document length,
  because short essays have unstable variance estimates.

### 2. `h010-polish-shorten` — ai_polished → human, confidence 0.63

An essay whose polish transform only removed hedges and a trailing sentence.

- A lightly edited essay is still mostly human text. Most sentences retain the
  original author's statistics, and the document aggregate is dominated by them.
- *This is the honest limit of the method*, not a tuning problem.

### 3. `h018-split_merge` — human → ai_polished, confidence 0.62

The same seed as case 1 with human editing noise applied — which suggests the error
is a property of that essay's style rather than of the specific variant.

Full write-ups with measured feature values, the true class's interquartile ranges,
and a proposed fix per case are in `failure_report.json` and on the Research page.

### Error breakdown

| Category                            | Count |
| ----------------------------------- | ----: |
| False positives on human writing    |     8 |
| Missed machine writing              |     0 |
| `ai_polished` confusions            |     6 |

Mean confidence when wrong is lower than when right, which is the desirable
ordering — the model is at least *less* sure when it is mistaken.

`features_version`, training configuration, platform and metrics.

## What would improve these numbers most

In order:

1. **Real human essays** in `data/raw/human/`. The 36-seed human class is the
   binding constraint on everything, and the dominance of corpus-similarity
   features is a direct symptom of it.
2. **Real model output** via the Groq generators, replacing the template generator.
   This will lower `ai_generated` from 1.000 to something informative.
3. **Real L2 writing**, collected with consent, so the bias question can actually be
   answered.
4. **Human documents in the held-out-topic and held-out-generator slices**, so
   cross-topic generalisation can be measured for the class that matters.
5. A larger instrument model (`LM_MODEL_NAME=gpt2-medium`) — better measurements at
   roughly 3× the cost.
